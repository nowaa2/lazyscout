Install and launch

LazyScout is a local application. The public website is documentation only; your QA workspace opens on your machine and Project data stays there.

RecommendedRun the latest published version
npx lazyscout@latest

For local development, start the API and web app in two terminals:

npm.cmd run dev:server
npm.cmd run dev:web
Local addresses Development UI: http://localhost:5173 · API server: http://localhost:4000

01 · PROJECTS

Create your first Project

Use one Project for each website or environment. Projects do not share Test Cases, credentials, Scout Logs, screenshots, or reports.

1Press New project in the sidebar.
2Choose Scout a website or create an empty import workspace.
3Enter the Target URL and choose the Test Case language.
4Press Scout Site and wait for Playwright to finish.
Existing data protection Scouting a Project that already has Test Cases opens a confirmation modal before replacement.

02 · DISCOVERY

Scout a website

Scout uses Playwright to visit same-origin pages, inspect accessible controls, observe UI states, and draft Test Cases for review. It follows links and clicks discovered navigation items, tabs, accordions and dialog triggers to map states — but it never fills or submits a form.

Login pages end a branch Any URL containing /login, /signin or /auth is treated as a lost session, and that action is rolled back — even when you were never signed in. Pages reachable only through a login link stay undiscovered until you use the authenticated workflow below.
Target URL

The website or path Playwright starts from.

Max pages

Hard limit for the number of pages inspected.

Max depth

How many link levels Scout follows from the starting page.

Language

Controls generated Steps, Expected Result, and generator notes.

Start Path

Continue from a page after login, such as /dashboard.

Scope Path

Keep discovery inside a section such as /admin.

Enable Include API checks from XHR/fetch when requests triggered by UI actions should appear in Test API. Increase Wait after navigation for slow client-rendered pages or delayed modals.

03 · AUTHENTICATION

Continue after login

Each Project has a persistent browser profile. Use it for normal form login, SSO, or a manual authentication step that cannot be automated safely.

  1. Scout onceProject Settings becomes available after the Project exists.
  2. Open Project SettingsAdd optional username, password, or token placeholders.
  3. Open login browserSign in manually in the browser launched by LazyScout.
  4. Close that browserThe Project profile keeps its cookies and local storage.
  5. Scout againSet Start Path to the first authenticated page and choose the scope.
Keep the hostname identical localhost and 127.0.0.1 are different origins and do not share cookies.

04 · DETERMINISTIC TESTING

Build a Guided Flow with the right locator

Guided Flow is for a tester-defined path. Add one step at a time, choose the locator that matches the real HTML, save the Flow, then run it with the real Playwright Test CLI.

Open the visual Guided Flow manual →
Rule of thumb Use CSS for inputs with a stable id or name. Use Role for buttons. Use Label when a real HTML label exists or when checking validation.

How to pair the page HTML with a Flow step

Open the browser inspector, select the element, and look for an id, name, label, role, placeholder, or data-testid. Pick the most stable unique value. Do not copy a long generated class name if a short id or name is available.

What you see in HTML Choose in Guided Flow Playwright that should be generated
<input id="username"> Fill → CSS → #username await page.locator('#username').fill(value)
<input name="password"> Fill → CSS → input[name="password"] await page.locator('input[name="password"]').fill(value)
<button id="submit">Submit</button> Click → CSS → #submit await page.locator('#submit').click()
<button>Submit</button> Click → Role → button → Submit await page.getByRole('button', { name: 'Submit', exact: true }).click()
<label for="email">Email</label> Fill → Label → Email await page.getByLabel('Email', { exact: true }).fill(value)
data-testid="save-button" Click → Test ID → save-button await page.getByTestId('save-button').click()
placeholder="Search products" Fill → Placeholder → Search products await page.getByPlaceholder('Search products', { exact: true }).fill(value)

Complete login example

For this HTML:

<input type="text" name="username" id="username">
<input type="password" name="password" id="password">
<button id="submit">Submit</button>

Configure the Flow like this:

Base URL: https://practicetestautomation.com
Navigate → /practice-test-login/
Fill → CSS → #username → TEST_USERNAME
Fill → CSS → #password → TEST_PASSWORD
Click → CSS → #submit
Wait → URL → /logged-in-successfully
Assert → URL → /logged-in-successfully

LazyScout should generate code equivalent to:

import { test, expect } from '@playwright/test'

test('Login', async ({ page }) => {
  await page.goto('https://practicetestautomation.com/practice-test-login/')
  await page.locator('#username').fill('{{TEST_USERNAME}}')
  await page.locator('#password').fill('{{TEST_PASSWORD}}')
  await page.locator('#submit').click()
  await expect(page).toHaveURL(/\/logged-in-successfully/)
})

Set TEST_USERNAME=student and TEST_PASSWORD=Password123 in Project Settings. Keep secrets out of Flow source and logs.

When a locator fails

Failure What it usually means What to change
strict mode violation More than one element matched. Add an id, test id, parent container, or use exact accessible name.
getByLabel found nothing The input has no real label or the label text differs. Switch to CSS using #id or [name="..."].
locator.fill timeout Wrong path, redirect, modal, or element is not visible. Verify Navigate URL, add Wait visible, then inspect the current page.
button click timeout Button name is different, duplicated, disabled, or covered by a modal. Use CSS id, Role with exact name, or add a modal close step first.
URL assertion failed The action did not navigate or the expected path is wrong. Copy the final URL from the browser and use only its path in Wait/Assert.

Repeated elements and nth()

Avoid a broad selector such as page.locator('button'). If several cards contain an Edit button, scope the button to the card or row first. Use nth() only when the page has no stable id, text, label, role, test id, or parent context. 

const row = page.getByRole('row').filter({ hasText: 'John Doe' })
await row.getByRole('button', { name: 'Edit', exact: true }).click()
Do not copy blindly Generate the Flow, open the Playwright code, and adjust only the locator or expected result that the real page requires.

05 · TEST DESIGN

Review and maintain Test Cases

Search or select a Module, filter by tags and status, then open the three-dot Action menu to view, edit, duplicate, or delete a case. Drag rows to reorder them.

Field What the tester should verify
Steps Actions are specific, ordered, and use safe test data.
Expected Result The result describes observable behavior, not only “works”.
Priority / Type Use them to create focused smoke or regression runs.
Requirement Add a Jira ID, GitLab issue, ticket, or requirement URL.
Execution Pending until run; then paired with the latest Pass or Failed result.

Import CSV, XLSX, or JSON from the toolbar. The image-to-Test-Case flow uses OCR as a starting draft; correct extracted text before saving.

06 · PLAYWRIGHT

Edit and run Automation

Choose cases with the run checkbox; Run all skips unchecked cases. Review generated Playwright code, press Run, then inspect the terminal-like log for each action and the final result.

  1. Select a Test Case and review its locator strategy.
  2. Edit code when login, upload, business data, or a precise assertion is required.
  3. Run one case or the selected suite.
  4. Open the related Bug Report when a case fails.
Screenshots are opt-in Add await page.screenshot(...) to Playwright code. LazyScout does not capture every page automatically.
Run executes the code you see LazyScout writes the editor contents to a temporary spec file and runs the real @playwright/test CLI. The code is not sandboxed and runs with your privileges — review it first. Limits per run: 100 steps, 200,000 characters, 20 seconds per action, 250 log lines. Cypress is code generation only.

07 · DIAGNOSTICS

Scout Log and Explorer

Scout Log records discovered pages, observed states, attempted actions, and completion issues. Explorer opens as a modal and groups the discovered pages and states so you can trace a generated Test Case back to its source path.

Two log lines explain most short crawls. Auth lost after action means the branch reached a login-looking URL and was rolled back. Failed: <name> means an action was retried twice and skipped; the run continues. A summary of browser-crash is a catch-all for any error inside the crawl — read the reported issue for the real cause.

08 · NETWORK

Test API requests observed by Scout

Test API lists XHR/fetch calls collected during UI actions. Run a safe request, add a Project token when required, and compare method, URL, status, duration, and result.

Unsafe methods require confirmation POST, PUT, PATCH, and DELETE are protected by default and limited to one execution when allowed.

09 · EVIDENCE

Bug Reports and screenshots

A failed automation run creates a Bug Report draft linked to its Test Case. Complete severity, reproduction steps, actual result, expected result, and evidence before sharing it. The Screenshots tab is a local gallery where images can be downloaded, deleted, or attached to a report.

10 · BASIC LOAD

Run a controlled Load Test

Set virtual users, requests per user, and the delay between requests. Start with small values and review status, duration, and Pass or Failed results in the request table.

Use only systems you own or are authorized to test This is a basic HTTP load check, not a replacement for a full JMeter performance plan.

13 · SAFETY

Know the safety boundaries

  • Scout stays on the target origin and configured path scope, and never fills or submits a form.
  • Destructive UI actions are allowed until you block them. Add keywords to the Project click filter in Project Settings — the built-in list is only a suggestion the UI offers.
  • Secrets stay in the active browser tab and are masked in logs by the redaction utility.
  • Artifacts are written unencrypted to your workspace folder. Review before sharing.
The runner is not a sandbox Run executes the code in the editor with the real Playwright CLI, at your user's privileges. There is no statement whitelist. Read the code before pressing Run, and never expose the LazyScout port — the local API has no authentication, so anything that can reach it can run code as you.

14 · HELP

Troubleshooting

The page stays on Login

Use the Project login browser, keep the hostname identical, close it after login, then Scout the authenticated Start Path again.

Scout creates no useful Test Cases

Check Scout Log for Cloudflare, authentication, delayed rendering, cross-origin navigation, or pages with no accessible controls.

Scout only found one or two pages

Open Scout Log. Auth lost after action means the branch hit a /login, /signin or /auth URL and was rolled back, which is expected on a site you have not signed into yet — use the Project login browser, then Scout again with a Start Path past the login page.

Port 4000 is already in use

Another LazyScout server is running. Stop it, or start yours elsewhere with PORT=4100 npm.cmd run dev:server. The packaged CLI picks the next free port automatically; the dev server does not.

Playwright Chromium is missing

Install the browser before using Scout. On Ubuntu/Linux, include the system dependencies:

# Windows / macOS
npx playwright install chromium

# Ubuntu / Linux
npx playwright install --with-deps chromium
