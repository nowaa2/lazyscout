01 · START HERE

Build the Flow in the same order as a real user

A Guided Flow is deterministic: LazyScout only executes the Steps you add. It does not crawl extra pages or guess what to click. Add Navigate first, then actions, then Wait or Assert for the result you expect.

1

Open the target page

Set Base URL once. Use Navigate with a path such as /login.

2

Inspect the element

In Chrome DevTools, right-click the control and choose Inspect. Look for id, name, label, role, placeholder, or data-testid.

3

Add one action

Choose Fill, Click, Select, Check, Wait, or Assert. Save and run after a few Steps instead of writing everything at once.

✓Before you Run, make sure the first Navigate step points at the exact real path. A valid selector cannot work on the wrong page.

02 · LOCATOR DECISION

Choose the locator from the HTML you actually have

Use the strongest stable attribute first. Do not choose Label just because the screen shows a word near an input: the page needs a real HTML label for that strategy.

The element has id or name→CSS
It is a button, link, checkbox, or tab with a clear name→Role
It has a real <label for="...">→Label
It has data-testid→Test ID
It has a stable placeholder→Placeholder
Only visible text is reliable→Text / Assert
!Avoid broad selectors such as button, input, or text that appears in many places. They may match the wrong element or cause a strict mode error.

03 · FILL INPUTS

Fill username, password, search, and textarea fields

Case A · Input has id or name

This is the most common login form. Choose CSS and copy a short stable selector.

<input type="text" name="username" id="username">
StepFill
StrategyCSS
Value#username
Value referenceTEST_USERNAME
await page.locator('#username').fill('{{TEST_USERNAME}}')

Case B · Input has a real label

Use Label only when the label is linked to the input with for and id, or wraps the input. 

<label for="email">Email address</label>
<input id="email" type="email">
StepFill
StrategyLabel
ValueEmail address
Value referenceTEST_EMAIL
await page.getByLabel('Email address', { exact: true })
  .fill('{{TEST_EMAIL}}')

Case C · Search with placeholder

Use Placeholder when the hint is stable and there is no better id, name, or test id.

<input placeholder="Search products" type="search">
StepFill
StrategyPlaceholder
ValueSearch products
Typed valueHeadphones
await page.getByPlaceholder('Search products')
  .fill('Headphones')

Case D · Test ID provided by developers

Test IDs are excellent for automation because visual copy can change without breaking the test.

<input data-testid="billing-postcode">
StepFill
StrategyTest ID

await page.getByTestId('billing-postcode').fill('10110')

05 · SELECT & CHECK

Dropdowns, checkboxes, radio controls, and toggles

Native select dropdown

<select id="country">...</select>
StepSelect
StrategyCSS
Value#country
OptionThailand
await page.locator('#country').selectOption('Thailand')

Checkbox or consent

<input id="terms" type="checkbox">
StepCheck
StrategyCSS
Value#terms
Checkedtrue
await page.locator('#terms').check()

Custom dropdown or menu

Custom menus are usually two actions: Click the menu trigger, then Click an option. Do not use Select unless it is a real <select>. 

await page.getByRole('button', { name: 'Country' }).click()
await page.getByRole('option', { name: 'Thailand' }).click()

Toggle switch

Use Check when it is an actual checkbox. For a visual-only switch, use Click then Assert its status text or attribute. 

await page.getByRole('checkbox', { name: 'Dark mode' }).check()
await expect(page.getByText('Dark mode enabled')).toBeVisible()

06 · WAIT & MODAL

Wait for navigation, a modal, a message, or a short delay

Prefer a meaningful wait over a fixed timeout. Use Timeout only for a small animation or third-party delay when there is no observable result to wait for.

Wait for URL after login

StepWait
Wait typeURL
Value/dashboard
await expect(page).toHaveURL(/\/dashboard/)

Wait for a modal to appear

StepWait
Wait typeElement visible
StrategyCSS
Value[role="dialog"]
await expect(page.locator('[role="dialog"]')).toBeVisible()

Wait for a success message

StepWait
Wait typeText
ValueSaved successfully
await expect(page).toContainText('Saved successfully')

Short fixed delay

StepWait
Wait typeTimeout
Value750 ms
await page.waitForTimeout(750)
!If a modal blocks a button, first Wait until the modal is visible, Click the close/cancel button, then continue. Do not wait 10 seconds hoping it disappears.

07 · ASSERT

Verify the result, not just that the click happened

Assert URL

Use after Login, navigation, or checkout.

await expect(page).toHaveURL(/\/logged-in-successfully/)

Assert visible element

Use for a dashboard heading, Logout button, or a modal.

await expect(page.getByRole('button', {
  name: 'Log out'
})).toBeVisible()

Assert success or error text

Use for validation, toast messages, and API feedback.

await expect(page.getByText('Your password is invalid!'))
  .toBeVisible()

Validation case

Click Submit with an empty field, then Assert the validation message. This is where Label and Text checks are often useful. 

await page.locator('#submit').click()
await expect(page.getByText('Email is required'))
  .toBeVisible()

08 · REPEATED ELEMENTS

When the page has many Edit, Delete, or Add buttons

Do not use a generic button selector and do not start with nth(). First locate the row, card, form, or modal that contains unique text, then locate the action inside it. 

<article class="user-card">
  <h3>John Doe</h3>
  <button>Edit</button>
</article>
const card = page.locator('.user-card').filter({ hasText: 'John Doe' })
await card.getByRole('button', { name: 'Edit', exact: true }).click()
✓Use nth() only as the final option when the order itself is a stable part of the product. If the page adds a new row later, a bare nth selector can click the wrong record.

09 · FULL EXAMPLE

A complete login Flow that you can copy

Base URL: https://practicetestautomation.com
1Navigate to the Login pageNavigate/practice-test-login/
2Enter the test usernameFill · CSS#username · TEST_USERNAME
3Enter the test passwordFill · CSS#password · TEST_PASSWORD
4Submit the formClick · CSS#submit
5Wait until Login navigation finishesWait · URL/logged-in-successfully
6Verify the final pageAssert · URL/logged-in-successfully 
import { test, expect } from '@playwright/test'

test('Positive login', async ({ page }) => {
  await page.goto('https://practicetestautomation.com/practice-test-login/')
  await page.locator('#username').fill('{{TEST_USERNAME}}')
  await page.locator('#password').fill('{{TEST_PASSWORD}}')
  await page.locator('#submit').click()
  await expect(page).toHaveURL(/\/logged-in-successfully/)
})

10 · FIX FAILURES

Read the CLI log, then change only the failing Step

The CLI tells you the exact generated locator it could not use. Find that Flow step and replace its Strategy or Value with a locator that matches the real page.

CLI error Meaning What to do in Guided Flow
strict mode violation One locator found more than one matching element. Use CSS id/test id, a more exact Role name, or a parent container + child selector. Avoid a broad Text locator.
waiting for locator('#username') The current page has no matching element. Check Navigate path first. Then inspect the element again and confirm its id/name was not changed.
getByLabel(...) found nothing The input has no linked HTML label, or the label wording is different. Switch to CSS with #id or input[name="..."].
button click timeout The button is hidden, disabled, named differently, duplicated, or covered by a modal. Add Wait → Element visible, close the modal, then use Role/CSS that targets the specific button.
URL assertion failed The action did not navigate, or the expected path is wrong. Copy the actual browser path and use its path portion in Wait URL and Assert URL.
Required test variable is not configured Value reference exists in the Flow but is empty in Project Settings. Add TEST_USERNAME, TEST_PASSWORD, TEST_EMAIL, or API_TOKEN in Project Settings, then run again.

The safe way to learn: one small Flow at a time.

Start with Navigate → one action → one Assert. When it passes, add the next action. This makes every failure obvious and keeps the final Test Case easy to maintain.
